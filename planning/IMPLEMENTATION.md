## Название и размещение

Предлагаемое имя — **RenoTrace**: renovation + trace, связь сумм ремонта с их источниками. Slug — `renotrace`. Исходная документация называется RenoLedger; это тот же продукт, а не второй проект. Исходные тексты и идентификаторы схем сохранены без переименования. Доступность бренда и домена не проверялась.

Рабочая папка: `D:\Новая папка\3 курс\Business Cup\renotrace`. Родительская папка содержит первоначальный комплект; разработка и Git ведутся внутри `renotrace`.

## Что следует из документации

- B2C для владельца жилья в США: объяснить текущий запрос подрядчика на оплату по уже существующим документам.
- Первая версия: один подрядчик, один редактирующий владелец, USD, английские документы и интерфейс.
- Результат — четыре самостоятельных блока: requested amount, remaining under recorded terms, payment conditions, unresolved questions. Остаток не является разрешением платить.
- Разделить публичный синтетический demo без регистрации и приватные пользовательские дела.
- Цена пилота $99, спрос и экономика пока являются гипотезами. Наличие документов и fixtures не подтверждает готовность продукта.

## Архитектурная основа

Используем уже выбранную архитектуру из `docs/05_ARCHITECTURE.md`: Next.js/TypeScript для UI и тонкого BFF; FastAPI/Pydantic для доменного API; PostgreSQL с SQLAlchemy/Alembic; отдельный worker из того же backend; приватное S3-compatible хранилище. Конкретные версии проверяются и фиксируются lockfiles в DEV-01.

Расчётное ядро `services/backend/app/ledger/` должно быть чистым Python-пакетом без HTTP, SQL, OCR и UI. AI возвращает недоверенные кандидаты по extraction schema; нормализация, решения пользователя и валидаторы формируют вход ядра. Все суммы — integer cents; отсутствующая база даёт `null`, а не нулевой остаток.

API и worker используют одну транзакционную модель: изменение фактов повышает case revision и ставит задание; публикация snapshot проверяет ожидаемую ревизию. Источники и snapshots неизменяемы; повтор задания не создаёт второй денежный факт. На всех приватных объектах проверяются tenant/case.

## На что обратить внимание при реализации

1. Проверка `validate_spec.py` сверяет уже нормализованные эталонные суммы. Она не реализует FIN-01…FIN-16: необходимо тестировать фактическую нормализацию, связи, версии и расчётное ядро.
2. Requested, commitments, billings, cash и allocations — разные сущности. Накопительный счёт, зачёт и возврат нельзя свести к простому суммированию файлов.
3. Подтверждение прочтения, трактовки, связи и актуальности должно оставаться независимым. Один boolean `verified` нарушит модель.
4. В demo изменение связи должно действительно пересчитывать результат тем же ядром; фиксированные итоговые карточки не выполняют критерий приёмки.
5. Контракты пока проектные. Перед реализацией каждого endpoint сверять OpenAPI, модель данных и его FR; выявленные противоречия исправлять явно вместе с контрактом.
6. OCR/LLM, identity, hosting и payment provider ещё не выбраны. Для подготовки ядра и синтетического demo это не препятствие; реальные файлы и платежи требуют соответствующих release gates.
7. В исходном плане указан дедлайн 15 ноября, 12:00, без подтверждённого часового пояса. Первый чат должен уточнить время и определить объём хакатонной поставки; полный коммерческий backlog не считать автоматически обещанным к этому сроку.

```sh
gh auth login
gh repo create IliasGalikhanov/renotrace --public --source=. --remote=origin --description "Trace renovation invoices, payments, and changes back to their sources." --push
```

Либо создать пустой публичный репозиторий через интерфейс GitHub, без README, лицензии и .gitignore, затем:

```sh

git push -u origin main
```

Эти команды — подготовленные инструкции, не выполненная публикация. Если имя занято или remote уже есть, сначала проверить существующий репозиторий. Не применять force push.
