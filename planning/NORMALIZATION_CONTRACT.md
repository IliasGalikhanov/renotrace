# Контракт нормализации структурированной истории

`app.normalization.normalize(HistoryInput) -> NormalizationResult`. Модуль чистый: не читает файлы, не обращается к HTTP, БД или AI. CLI читает JSON снаружи модуля и передаёт полученный `LedgerInput` настоящему `app.ledger.calculate`.

## Вход и источники

Все модели immutable, strict, запрещают лишние поля. JSON-даты — ISO calendar date; timestamps аудита — UTC с явным timezone. Суммы — целые центы в диапазоне ±9 000 000 000 000; отсутствующая сумма — `null`, а не ноль. Все записи относятся к одному case, подрядчику и USD; cutoff включителен.

- `Source`: устойчивый ID конкретного источника/версии, case_id, version, origin, locator и actor_id при наличии. Ссылка на источник должна существовать в переданном реестре и принадлежать тому же case. Наличие записи в реестре не проверяет существование или содержимое реального файла.
- `Record.id`: неизменяемый ID ревизии. `record_id`: логический ID события, общий для его версий. Пара `(record_id, version)` уникальна; вид записи не меняется между версиями.
- Виды: `agreement`, `adjustment`, `cash`, `payment_request`, `billing`, `allocation`. Счёт с `mentioned_deposit_cents` сохраняет упоминание, но не создаёт денежного события.
- `origin`, `review.extraction_review`, `review.semantic_review`, `review.lifecycle` независимы. Проверенное извлечение не подтверждает смысл. Для проверок записываются actor и timestamp; пользовательское принятие смысла не превращает `user_statement` в `bank_record`.
- Cash содержит состояние и знаковую сумму: платёж положительный, возврат отрицательный. Необязательная банковская идентичность задаётся только полной парой `bank_account_id` + `bank_transaction_id`. Контекст счёта должен быть устойчивым и включать namespace провайдера, если разные провайдеры могут выдавать одинаковые ID.

## Связи и решения

`Link` содержит ID, `from_id`, `to_id`, kind, независимый review, basis_revision и evidence_refs. `supersedes` направлен от новой сметы к старой; `includes_adjustment` — от сметы к включённому изменению. Для принятой/отклонённой связи нужны actor/timestamp. Одна пара концов одного вида представлена одной связью. Циклы и неверный порядок ревизий/дат замены отклоняются; проверяется весь объявленный граф, включая предложенные/отклонённые связи.

Каждое решение содержит собственный ID, actor, decided_at, evidence_refs и basis_revision:

| kind | target_id | Значение |
|---|---|---|
| select_version | логический record_id | selected_id ревизии либо null |
| select_agreement | case_id | selected_id сметы либо null |
| assign_contractor | ID ревизии записи | contractor_id либо null |
| confirm_semantics | ID ревизии записи | accept / reject / unknown |
| review_link | ID связи | accept / reject / unknown |

Используются решения для текущей case_revision. Несколько одинаковых решений сохраняют источники всех подтверждений. Разные текущие ответы по одной области создают `DECISION_CONFLICT`, без правила «последняя загрузка выигрывает». Старое решение без нового подтверждения блокирует свою область с `STALE_DECISION`; явное текущее решение заменяет старое. Исходные записи и флаги не переписываются: effective значения и applied decisions возвращаются отдельно.

## Выбор истории

1. Неподходящие lifecycle/даты исключаются с причиной; stale дополнительно создаёт вопрос. Неопределённый смысл, получатель или сумма требуют уточнения. Явный другой подрядчик исключается.
2. Не выбирается максимальная версия по номеру или последняя загрузка. Версии платежей/изменений требуют явного выбора; для смет действуют также подтверждённые связи замены. Несколько независимых действующих смет дают конфликт и `null` базы. `select_agreement` может выбрать подходящую незаменённую смету.
3. Выбор старой версии не отменяет принятую замену автоматически: сначала надо разрешить противоречащую связь. Подтверждённая новая смета исключает заменённых предшественников.
4. Явное включение изменения в выбранную смету исключает повторное прибавление. Неясная связь включения исключает спорное изменение и ставит вопрос. Включение в предшественника не считается автоматически подтверждённым для новой базы: без прямого подтверждения возвращается вопрос о покрытии изменения.
5. Только completed cash установленному подрядчику до cutoff включительно поступает в ledger. Возврат влияет на P, не C. Состояния pending/scheduled/failed/reversed не учитываются как completed.
6. Банковские наблюдения группируются по паре счёт/операция внутри case. При одинаковых сумме, дате, состоянии и установленном подрядчике считается одна операция, источники объединяются. Разные ID операций и операции разных счетов сохраняются независимо от одинаковой суммы.
7. Противоречие суммы/даты/состояния/получателя одной операции исключает всю группу с вопросом. Проверка конфликтов проводится до cash cutoff, чтобы противоречащая дата не скрывалась за фильтром. Неразрешённую версию той же операции нельзя обойти другим импортом. Непроверенный смысл одного наблюдения не замалчивается в пользу другого.
8. Канонический ID банковского события детерминирован парой счёт/операция. Новый повторный импорт не создаёт ещё один денежный факт; его новый источник может расширить provenance. Без банковской идентичности сходство сумм не используется для объединения.

С версии `normalization-0.1.1`, если часть согласованных по финансовым полям подтверждений допускается к учёту, а другая часть отклонена или ещё не разрешена, вся операция остаётся исключённой до уточнения. Вопрос `TRANSACTION_REVIEW_CONFLICT` перечисляет все записи группы и связанные решения (в том числе устаревшие, необходимые для объяснения), влияет на `net_paid_cents` и `remaining_commitment_cents`. `incomplete=true`; обе метрики включены в `incomplete_metrics`. `decision_ids` вопроса — контекст уточнения, а не утверждение, что все эти решения применены.

Когда все подтверждения приняты, учитывается один платёж и конфликт исчезает. Когда все согласованные по финансовым полям подтверждения явно отклонены текущими решениями, они получают `REJECTED_BY_USER`: само по себе это намеренное исключение не создаёт вопроса или неполноты. Непроверенное или устаревшее решение не считается намеренным отклонением.

Смешанное происхождение нескольких подтверждений одной операции обозначается `derived`; исходное origin каждого наблюдения сохраняется в аудите. Это не утверждение банковской проверки.

## Выход и ошибки

`ledger_input` содержит отобранные числа для ledger. `included` и `excluded` вместе покрывают каждую входную ревизию ровно один раз, с причиной, каноническим ID при наличии, evidence refs, применёнными решениями и effective признаками. Отдельно возвращаются реестр sources, исходные links и applied_decisions. `CURRENT_REQUEST` связывает отдельное requested значение с источником текущего счёта.

`questions` содержат устойчивый ID, code, record_ids, decision_ids для конфликтов решений, affected metrics и пояснение. Порядок детерминирован; UI-приоритизация вопросов не реализована. `incomplete` и `incomplete_metrics` нельзя терять при показе частичного итога: исключённая спорная запись может менять сумму после уточнения. Ledger сам не интерпретирует эти флаги.

Инвариант: для каждой записи, исключённой как `UNRESOLVED_TRANSACTION`, существует вопрос с её ID, затрагивающий одновременно `net_paid_cents` и `remaining_commitment_cents`. Итог помечен предварительным по обеим метрикам. Это проверяется общей проверкой всех нормализационных сценариев и генеративными комбинациями подтверждений.

Повреждённая структура (несуществующие ссылки, повторные ID/версии, чужой case, циклы, некорректные концы связей) вызывает `NormalizationError` со стабильным `code` до выдачи результата. Неверные типы/диапазоны/аудитные поля вызывают Pydantic `ValidationError`. CLI в обоих случаях возвращает exit code 2 без финансового JSON.

Повтор вызова не меняет вход и не создаёт события. Перестановка записей, источников, связей и решений не меняет выход и ledger fingerprint. Чистая функция не увеличивает case_revision и не обеспечивает DB-idempotency: сохранение решений, увеличение revision, авторизация actor и транзакции остаются обязанностями будущего слоя приложения.

Автоматическое извлечение/распознавание смыслов документов, неопределённые даты и локали не реализованы этим контрактом. Обновлённая structured history с явными решениями является входом, а не результатом OCR.

## Этап 3: начисления и распределения

Версии: `normalization-0.2.0`, `ledger-0.2.0`. Старые поля C/P/R/requested сохраняют формулы; новые коллекции `LedgerInput.charges`, `billing_credits`, `allocations` по умолчанию пусты. Новые поля и версия правил меняют fingerprint относительно этапа 2, даже если старые суммы совпадают.

### Типизированное покрытие и независимая проверка связей

`Billing` и `PaymentAllocation` наследуют immutable ID/record_id/version, дату, сумму, подрядчика, evidence_refs, origin и независимые extraction/semantic/lifecycle признаки. Дополнительно оба содержат `basis_revision`, `relationship_review` (`proposed/accepted/rejected/invalidated`), `relationship_actor_id`, `relationship_reviewed_at`. Для accepted/rejected обязательны actor и UTC timestamp; evidence_refs записи обосновывают также её отношения. Семантическое подтверждение не принимает связь автоматически.

Включается только accepted связь текущей case_revision. Proposed/invalidated и устаревшая база требуют уточнения; rejected текущей ревизии — намеренное исключение. Изменение этих структурированных утверждений оформляется новой ревизией записи с источником и аудитом, а выбор между активными версиями — существующим `select_version`. `review_link` относится к отдельным Link смет и не изменяет вложенные отношения billing/allocation. `confirm_semantics` не переписывает relationship_review.

### Billing

| Поле | Значение |
|---|---|
| basis | incremental_charge / cumulative_valuation / balance_statement / credit_note / unknown |
| coverage | Набор устойчивых ID атомарных объёмов/периодов работ в данном case |
| coverage_confirmed | Явное подтверждение, что этот набор полностью описывает область начисления |
| previous_id | ID конкретной предыдущей ревизии начисления для cumulative_valuation |
| starts_at_zero | Только для первого cumulative: явно подтверждённое отсутствие предыдущего начисления |
| credit_target_id | ID конкретного начисления, которое корректирует credit_note |

`coverage` — подтверждённое разбиение работ, а не произвольные номера документов: разные атомарные ID утверждают независимость объёмов. Присвоение корректных ID выполняется до нормализации; модуль не доказывает непересечение по тексту. Пустой/неподтверждённый набор требует вопроса. Пересекающиеся независимые начисления или две ветви накопительного ряда исключаются с вопросом, без выбора последней загрузки. Перестановка записей не выбирает победителя.

- `incremental_charge`: неотрицательное самостоятельное начисление после проверки покрытия.
- `cumulative_valuation`: исходная сумма неотрицательна. Предыдущая запись должна быть принятой, иметь точно тот же набор coverage, вид incremental/cumulative и дату не позже текущей. Приращение = текущая исходная сумма − предыдущая исходная сумма; сумма предыдущей оплаты не используется. Последовательность обрабатывается по зависимостям, а не порядку входа. Отрицательное приращение сохраняется. Первый cumulative требует `starts_at_zero=true`; отсутствие предыдущего начисления не означает нулевую базу.
- `balance_statement`: сохраняется в аудите как `BALANCE_STATEMENT_ONLY`, не создаёт начисление или платёж. Requested задаётся отдельным `payment_request` и `current_request_id`; обе записи могут ссылаться на один источник.
- `credit_note`: строго отрицательная сумма с явным выбранным целевым начислением. Сумма корректирует его billed amount, не создаёт отдельную позицию для распределения денег и не меняет C/P. Coverage берётся у целевой позиции. Изменение C требует отдельного commitment adjustment; движение денег — отдельного cash event.
- `unknown`: вопрос `UNKNOWN_BILLING_BASIS`, вклад не включается.

Накопительные суммы в этом контракте — gross valuation до отдельно записанных credit notes. Если документ уже содержит зачёт внутри cumulative, его нельзя также передать отдельной credit_note: такой смысл необходимо разрешить до входа. Произвольное частичное пересечение областей не пересчитывается пропорционально: требуется уточнение/новая структурированная история. Credit note не меняет исходную предыдущую gross valuation при вычислении следующего приращения.

Канонические начисления и кредит-ноты имеют ID `record:<revision-id>`. Приращение имеет origin=derived; его evidence_refs включают всю цепочку предыдущих начислений и применённых решений. Credit note дополнительно ссылается на доказательства цели; исходные значения и независимые проверки доступны в dispositions.

### Allocation

Поля: `cash_id` (ID входного наблюдения cash), `charge_id` (ID ревизии billing), знаковый `amount_cents`, необязательный `reverses_allocation_id` (ID исходного положительного распределения). Все references должны существовать и иметь правильный тип. Сумма ненулевая; положительное распределение не может иметь reverses, отрицательное обязано иметь его.

1. Cash разрешается в каноническое денежное событие после выбора версий и банковской дедупликации. Ссылка на любой согласованный дублирующий импорт ведёт к тому же событию и той же доступной сумме. Исключённая версия, спорная операция, чужой подрядчик, незавершённый или будущий платёж недоступны; зависимое распределение исключается с вопросом.
2. Charge должна быть принятой ревизией incremental/cumulative. Credit note, balance statement и неизвестное начисление не являются целями распределения.
3. Разрешены частичные связи многие-ко-многим. Равенство сумм ничего не связывает. Для каждого канонического cash сумма модулей распределений не превышает модуль cash; направление совпадает. Возврат не увеличивает повторно доступную сумму исходящего платежа.
4. Отрицательное распределение указывает исходное положительное распределение к той же charge. Совокупные возвраты не могут обратить больше его суммы. При неразрешённом исходном распределении возвращается вопрос; сам completed refund остаётся в P и его нераспределённой части.
5. Возврат без allocation не угадывает счёт или платёж: он остаётся отрицательной нераспределённой суммой. Источник credit_note не является доказательством денежного возврата.
6. Распределение не может предшествовать датам cash/charge, его корректировка — исходному распределению, а credit_note — целевому начислению.
7. Каждое логическое allocation имеет устойчивый record_id. Повторная обработка не создаёт событие; несколько активных ревизий требуют выбора. Два разных record_id считаются двумя явными распоряжениями, а не объединяются по равной сумме; агрегатные лимиты проверяются совместно.

Ledger повторно проверяет ID, типы связей, существование и completed state cash, знак, лимит каждого денежного события, цель credit note и лимит обратных распределений. Неверные суммы/направления дают ValidationError без финансового результата, а не усечённую сумму. Неверные исходные ссылки, циклы cumulative и порядок дат дают NormalizationError. Концы, которые существуют, но пока не разрешены, дают вопросы и предварительные значения.

### Результат ledger и неполнота

| Поле | Формула/смысл |
|---|---|
| billed_total_cents | B = сумма приращений + credit notes |
| charge_balances[].charge_cents | Признанное начисление позиции с её credit notes |
| charge_balances[].net_allocation_cents | Сумма положительных распределений и связанных отрицательных корректировок |
| charge_balances[].remaining_cents | charge_cents − net_allocation_cents, со знаком |
| positive_outstanding_cents | Сумма положительных remaining по позициям |
| credit_balance_cents | Положительный модуль суммы отрицательных remaining по позициям |
| net_allocations_cents | Знаковая сумма всех allocations |
| unallocated_cents | U = P − net_allocations; допускается отрицательное значение |
| cash_balances[] | Для каждого completed cash: amount, net_allocation и unallocated |

Для каждого cash: `amount = net_allocation + unallocated`. Для каждой charge: `remaining = charge − net_allocation`. Сумма остатков позиций = positive_outstanding − credit_balance. Эти значения не означают наступление срока оплаты.

Вопросы billing затрагивают B, charge_balances, positive_outstanding, credit_balance и зависимые распределения/U/cash_balances. Вопросы allocation не затрагивают C/P/R/requested. Вопросы cash теперь дополнительно отмечают неопределённость связанных распределений/U; инвариант этапа 2.1 для P/R сохранён. `incomplete_metrics` содержит имена как денежных агрегатов, так и коллекций остатков; это консервативная отметка для всей коллекции, не отдельный статус каждой строки.

Ноль B при отсутствии принятых начислений означает сумму учтённых записей, не доказательство отсутствия счетов в реальном мире. Частичные итоги всегда сопровождаются normalization.questions/incomplete_metrics. Синтетические исходные истории этапа 3: [billing_cases.json](../fixtures/billing_cases.json); они проходят через настоящий normalize → calculate.
