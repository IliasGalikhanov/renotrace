# Stage 8: explicit invoice rechecks and frozen comparisons

API `0.8.0`, calculation snapshot contract `guest-review/3`, comparison algorithm `invoice-comparison/1`. Extends [guest reviews](GUEST_REVIEW_CONTRACT.md) and [casework](CASEWORK_CONTRACT.md). USD, original 24-hour guest lifetime, same owner checks/private originals and OCR. No outgoing messages, paid package or extended access. Stage 9 adds version-consistent PDFs through the separate [export contract](PDF_EXPORT_CONTRACT.md); financial and comparison semantics stay unchanged.

## Workflow and actual API

Stage 10 clarifies the legacy saved key `new_questions`: it contains cards first recorded since the previous snapshot, including inactive historical cards. It is not a list of new active problems. UI/PDF label these cards using their saved `observation.active`; original-question findings use the selected comparison's `new_snapshot_id` discussion. The UI reads that immutable snapshot, never today's discussion or a rerun of the calculation. Reassessment remains separate from presence. Stored comparisons and `invoice-comparison/1` are unchanged.

The owner chooses an existing snapshot, starts a persisted recheck draft, uploads documents through the existing transfer pipeline, selects replies/versions and source files, reviews financial facts and invoice positions, saves the package, and explicitly runs the recheck. Upload or package save alone never produces a completed comparison. Existing **Save review and calculate** remains available; financial form changes are committed only by that action or **Run recheck**. Unsaved form edits are not an autosaved draft. The package is independently saved and survives reload/restart.

Routes below start `/api/guest/projects/{project_id}` and use the existing bearer ownership/expiry check and same-origin BFF allowlist. Full typed schemas are exported to `contracts/demo.openapi.json` from the real FastAPI app.

| Method / suffix | Behavior |
| --- | --- |
| GET project | Existing response plus `result.invoice_compositions` and `rechecks` containing drafts and comparison summaries, including a live `current` flag. |
| POST `/review` | Existing review plus `invoices` and `request_versions`; same financial-save transaction and immutable snapshot as explicit rechecks. |
| POST `/rechecks` | UUID `mutation_id`, owner-scoped `base_snapshot_id`. Creates a draft, no financial save. |
| POST `/rechecks/{draft_id}/package` | UUID, `expected_version`, typed `package`. Pins source files, reply IDs and exact version numbers, old/new request, relationship, confirmed one-to-one row mappings and original-question evidence links. |
| POST `/rechecks/{draft_id}/run` | UUID, `expected_version`, full existing typed `review`. Rechecks current document revision, saves real normalization → ledger and a new full snapshot, stores immutable comparison of the selected old/new snapshots, marks the draft completed, all atomically. |
| GET `/comparisons/{comparison_id}` | Frozen JSON and algorithm version, both snapshot IDs and timestamp. Does not call normalization, ledger or the comparison algorithm. |

Project/draft/snapshot/reply/file/page IDs must exist within the authorized project. Retry IDs are checked only after ownership. 404 for missing/foreign/expired entities; 409 for changed draft/revision, completed recheck or a retry UUID reused for different content; 422 for incompatible lineage, invalid money or correspondence; 429 for capacity. Identical successful retries do not create another snapshot, comparison, reply or cash event. A completed draft cannot be edited or rerun with a new mutation ID; start another recheck instead.

Package document selection includes the compared invoice and every source added since the base snapshot. Existing financial evidence remains part of the case; omitting an old file from the package does not remove it from the ledger. Reply versions can be explicitly chosen, including an earlier version; selected text, provenance, actor, time and attachments are frozen in the comparison. Later reply edits invalidate current applicability without mutating old text/results. Replies remain owner-reported, never independently received or automatically interpreted.

## Invoice composition and request versions

Each reviewed invoice identifies an immutable file and a payment-request candidate. Each position has a stable ID, optional original proposal ID, meaning, description, nullable USD amount, source page, manual review state (`checked`, `unknown`, `excluded`), optional source-stated quantity/unit price and optional existing-payment candidate link. Correcting an extracted row preserves its proposal ID. Manual additions have independent stable IDs and a real source page. Original extracted text is never overwritten; output distinguishes checked extraction, manual correction and manual entry.

Position meanings: work, charge, discount, credit/allowance, reflected payment, condition, unknown. Monetary inputs are nonnegative decimal strings converted on the server into bounded integer cents; discounts, credits and reflected payments subtract in document arithmetic. Conditions are text, not money. Quantities use Decimal only to check a supplied unit-price × quantity against the stated amount; no missing value or rounding is invented. Unknown/excluded lines do not silently become checked totals. Composition reports checked total, requested total, unexplained difference and explicit completeness issues. Owner assertion of completeness does not override missing proposals, unknown values, unreadable sources or a reconciliation mismatch. There is no balancing row.

Recognition is deliberately limited: on pages containing “invoice”, labelled English rows such as `Work [surface]: Surface preparation | USD 6,200.00`, `Discount [id]: ... | USD ...`, `Credit [id]: ... | USD ...`, `Payment reflected [id]: ... | USD ...`, and `Condition [id]: ...` become proposals. Optional `| Qty: 2 | Unit: USD 10.00` is retained when present. Text PDFs and existing Tesseract OCR feed this same parser. Arbitrary layouts/tables and ambiguous currencies are not claimed as automatically understood. Unrecognized content can be manually added with a source page. USD amounts still require owner review.

Rows never become contract adjustments, charges in the ledger, cash transfers or allocations. Existing normalization/ledger remain the only source of C/P/R and the other financial indicators. A reflected-payment row may cite only an existing payment to this contractor. Normalization resolves that candidate to the canonical completed cash event, including bank-ID duplicates. Missing/excluded/pending cash produces uncertainty, and summed reflections above the available canonical amount are rejected. Crediting an allowance without a payment link does not prove a missing payment was reflected.

`request_versions` is a separate history of explicit old → corrected payment-request relationships. It is never passed to the agreement `supersedes` logic. Both candidates must be accepted invoice requests in different files for the same contractor; the current selected request cannot be a replaced predecessor. Dangling links, cycles, duplicate/branching/conflicting replacements are rejected; recorded history cannot be silently removed. A recheck independently declares `same`, `corrected`, `separate` or `unknown`. A corrected recheck must include its exact confirmed request-version pair. Separate/unknown invoices cannot assert that pair. Upload order, filename, amount and date do not choose a successor.

## Comparison semantics and uncertainty

Confirmed correspondences are one-to-one old/new position IDs; a null old side explicitly means added, a null new side means removed. Unknown/repeated IDs are rejected. Identical stable IDs in a same-invoice recheck can retain identity. For different documents, equal description plus kind can suggest possible matches; amount alone never does, and suggestions are not accepted automatically. Unmatched or unchecked rows remain explicit gaps. Historical snapshots without invoice composition remain incomplete; old detail is never backfilled from today's parser.

Frozen output includes added/removed/changed/unchanged rows, changed descriptions/amounts/quantities/unit prices/kinds/payment links, both checked compositions and unexplained differences, unmatched rows, suggestions, old/new payment conditions, original-question findings and new questions. Work/charge additions or changes require checking approval separately. No invoice reduction is labelled savings.

Requested amount deltas and C/P/R deltas are shown separately, using the two stored real ledger results. Comparison arithmetic does not calculate contractual balances. Original-question findings can report an explicit checked invoice credit/reflection only when an owner linked that position to the question and to a canonical payment already present in the base ledger. The recorded position amount and both sources remain inspectable. A lower invoice total alone never establishes that a missing payment was accounted for.

Comparison evidence does not automatically change card evidence state, owner decision, incomplete metrics or money. Partial/conflicting replies remain owner-reported and require human assessment. Disappearance, acceptance or stopping clarification is not resolution. Current sources, financial review, replies and assessments are fingerprinted; changes mark comparison summaries **Needs recheck** while the saved comparison stays byte-for-byte unchanged. This invalidation is deliberately conservative, including unrelated new evidence. Historical displays always say read-only.

## Persistence, migration, rollback and bounds

Three additive PostgreSQL tables: `invoice_state`, `rechecks`, `comparisons`, all project-owned with cascade deletion/expiry. An UPDATE trigger rejects changes to comparisons, just as for snapshots. Read/write transactions lock the project; invoice side data is read after acquiring that lock to avoid mixing a new project row with an old pre-lock MVCC snapshot under concurrent retries.

The original `projects.data` shape remains stage-7-compatible. New invoice proposals and review fields are held in `invoice_state`; the saved review ID gates rehydration. This permits an older backend to read existing cases during rollback. If an old backend saves a new review, old invoice-review fields are not silently reattached to that new review on upgrade. Frozen snapshots/comparisons remain intact. Apply migration before backend deployment, deploy backend before frontend, and preserve all additive tables on rollback. Roll back frontend first; retain the hourly cleanup and original expiry. Never reconstruct deleted/expired data.

Existing limits remain; additionally up to 20 recheck packages, 100 positions per invoice, 20 invoice compositions/lineage links, 200 correspondences and 100 question-position links per package. The existing 20-snapshot cap also bounds completed comparisons. These are technical free-resource bounds, not paid feature restrictions; every submitted new charge is displayed. No new dependency, paid service or permanent account is introduced.
