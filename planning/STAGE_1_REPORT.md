# Этап 1: каркас и финансовое ядро

Проект: **RenoTrace**. Папка: `D:\Новая папка\3 курс\Business Cup\renotrace`.

## Реализовано

- Next.js 16.4.6 / React 19.3.1 / TypeScript 5.9.3: запускаемая стартовая страница, production build, проверка типов.
- Python 3.13.18 / FastAPI 0.162.7: `GET /healthz`; остальные бизнес-маршруты не реализованы.
- Чистый `app.ledger`: immutable strict Pydantic-модели, integer cents, выбранная база и изменения, completed payments/refunds, отдельные requested amount и remainder.
- Неизвестная база сохраняет `null`; известная нулевая база отличается от неизвестной; отрицательный остаток не обнуляется.
- Каждый вход и опубликованная сумма проверяются на диапазон ±9 000 000 000 000 центов; float, bool, строки и Decimal вместо int отклоняются. Промежуточные суммы используют точные Python int.
- Повтор одного record ID отклоняется, два одинаковых по сумме события с разными ID сохраняются. Это контроль входной целостности, не автоматическое распознавание дублей документов.
- Result содержит ссылки на участвовавшие record IDs, исключённые незавершённые cash events, case revision, rules version и независимый от порядка input fingerprint.
- CLI для FIN-01…FIN-16 и нормализованного JSON; ошибки возвращают ненулевой exit code.
- `uv.lock`, `package-lock.json`, локальная установка через PowerShell, `.env.example`, README, CI на Windows/Linux и постоянное правило проверки функций в `CONTRIBUTING.md`.

## Границы выполненного этапа

Fixtures содержат готовую нормализацию. Тесты вызывают настоящий ledger, но не доказывают OCR, извлечение, поиск дублей, выбор версий, распознавание накопительного счёта, зачётов или получателя. Эти решения уже внесены в fixture; адаптер только переводит его числовые массивы в типизированные записи.

`expected_issue_codes`, billing entries, allocations и условия этапа не рассчитываются в этой поставке. Нет базы данных, очереди worker, identity provider, загрузки документов, отчётов, оплаты и production deployment. Веб-страница не является готовой продуктовой demo. Полное покрытие маленького ядра не подтверждает корректность будущего полного продукта.

Следующий этап — нормализация событий и связей документов — не начат. Его объём задаёт первый чат после приёмки.
